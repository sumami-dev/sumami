FAQ

Common questions about running Sumami. If yours is not here, the issue tracker is the place to ask.

General

How is this different from Umami?

Sumami is an independent open-source project that implements the Umami v2 HTTP API. It is an open-source alternative to Umami: the official Umami dashboard and the Umami tracker work against it unchanged. What differs is the packaging — Sumami ships as a self-contained service with a single DuckDB file and no external database, no PostgreSQL and no ClickHouse — and the privacy defaults, which are cookieless by construction.

Sumami is not affiliated with, endorsed by or sponsored by the Umami project, and no Umami assets — logo, artwork, code or copy — are used.

Do I need a domain?

No. You can run it on http://localhost:3999 and collect data from a local site. A domain and TLS are only needed if you want to serve it publicly, which in turn is needed if the sites you measure are not on localhost — a browser will refuse a mixed-content request to an insecure origin.

What are the system requirements?

A 64-bit Linux box (or macOS), 1 vCPU, 512 MB of RAM and about 30 MB of disk for the program. The database grows with your traffic but stays small: a page view is a few dozen bytes. DuckDB runs with an explicit 256 MB memory limit by default so a 512 MB box survives.

Why DuckDB and not SQLite or PostgreSQL?

DuckDB is an analytical database: it is fast at the aggregations analytics is made of (grouping and counting over time ranges), it has first-class JSON, and it writes to a single file with no server to run. SQLite would be fine for many workloads but is weaker at the aggregate queries the statistics endpoints issue. PostgreSQL would need a second process to operate, which is exactly what this design is trying to avoid.

Can I use the official Umami dashboard?

Yes — that is the point of the compatible API. Point the Umami dashboard at your Sumami host and log in with the admin account. Alternatively, Sumami serves its own small dashboard shell at /, loading the frontend from js/ or from a CDN if you set SUMAMI_APP_URL.

Does it support multiple websites?

Yes, without any extra configuration. Create one website per site in the dashboard and give each its own tracker snippet. Each website has its own retention window and its own country-header setting.

Installation

What is libduckdb.so and why is it missing?

DuckDB is linked dynamically, which is what keeps the executables at a few megabytes each instead of tens. The shared library comes from the DuckDB releases page and is included in the Sumami release archive. If you get an error like error while loading shared libraries: libduckdb.so, the library is not where the loader expects it.

Either install it on the loader path:

sudo install -m 0755 libduckdb.so /usr/local/lib/
sudo ldconfig
ldconfig -p | grep duckdb

Or keep the three files together and tell the loader where to look: 

export LD_LIBRARY_PATH=/opt/sumami

On macOS the file is named libduckdb.dylib and the variable is DYLD_LIBRARY_PATH.

Can I move the database file to another machine?

Yes. Stop the service, copy the .duckdb file (and the .jwt-secret file next to it, if you want existing tokens to keep working), and start the service on the new box. Because the visitor identifier is derived from the server secret, changing the secret means visitor identifiers change — which is a privacy feature, not a bug.

Where did my admin password go?

On the very first start on an empty database, the server creates the admin user. If SUMAMI_ADMIN_PASSWORD was not set, the generated password is printed to the log once and never again. 

sudo journalctl -u sumami | grep 'password:'

If you have lost it, set a new one: 

sumami-server admin --db /var/lib/sumami/sumami.duckdb \
  --username admin --password 'a-new-long-passphrase'

How do I change the port?

The --port flag or the SUMAMI_PORT environment variable, or sudo systemctl edit sumami for a systemd deployment. The default is 3000.

Operating

My page views are not showing up. Where do I start?

Work through these in order:

  1. Is the request being made? Open the developer tools on your site, go to the Network tab and look for POST /api/send. No request means the tracker script did not load, or the visitor's browser has DNT or GPC enabled and the tracker correctly sent nothing.
  2. Does it return an error? A 400 unknown website: … response means the website id or domain does not match anything the server knows.
  3. Is the data committed? Reads only see data that has been flushed, which happens every SUMAMI_FLUSH_INTERVAL_SECS seconds — two by default. Wait a moment and reload.
  4. Are you looking at the right window? The statistics endpoints default to the last seven days.
  5. Is the proxy in the way? Check the server log for /api/send requests. If there are none, the request is not reaching the server — a Content Security Policy that blocks your analytics domain is the usual culprit.

What does "the 33rd kitty was too cute to count" mean?

It is the log line for the queue overflow handler. If more events arrive than the write buffer can hold — SUMAMI_MAX_QUEUE, 100000 by default — the server drops the oldest buffered events instead of growing until the OOM killer arrives. Statistics do not need to be perfect; the server staying up matters more. The number of dropped events is in /api/heartbeat as dropped.

If you see this regularly, raise SUMAMI_MAX_QUEUE and the DuckDB memory limit, or check that the disk is not full.

Can I run two instances against the same database?

Do not. DuckDB takes an exclusive lock on the file. One server writes; the CLI may read it when the server is stopped. Use sumami prune --url … and sumami erase --url … to make changes through a running server instead of touching its file.

Does it need HTTPS?

Not technically, but practically yes for anything public: a browser will not send an insecure request to an insecure API from an HTTPS page, and you should not run an analytics endpoint over plain HTTP in public. There are two ways to get it. Put a reverse proxy in front — Caddy or nginx — and it will obtain and renew a Let's Encrypt certificate over ACME for you. Or let Sumami manage the certificate itself with --ssl example.com: it obtains and renews the certificate over ACME in the background, with no certbot and no cron job. The self-hosting guide has the configuration for both.

With a reverse proxy, the proxy terminates TLS and the server sees plain HTTP on loopback. With --ssl, the server terminates TLS itself and port 443 has to reach it directly.

How do I get a certificate?

Either through the reverse proxy or from the server itself.

Through the reverse proxy: Caddy does it with three lines of configuration; nginx does it with certbot. Both renew automatically. You need port 80 reachable from the internet and the domain's DNS record pointing at the server — a DNS record that has not propagated yet is the most common cause of a failed first issuance. If port 80 is closed, use the DNS-01 challenge instead.

From the server itself: sumami-server serve --ssl example.com --ssl-email you@example.com. The certificate is issued by Let's Encrypt over ACME and renewed in the background. The challenge is TLS-ALPN-01, so port 443 must reach the Sumami process directly — no proxy in front of it. Port 80 does not need to be open. Back up the cache directory (by default an acme directory next to the database, e.g. /var/lib/sumami/acme): it holds the ACME account and the certificates, and losing it means re-issuing.

How do I back it up?

One file. Stop the service, copy sumami.duckdb somewhere safe, start the service again. The self-hosting guide has a ready-made script and a cron entry. Copy the .jwt-secret file too if you want issued tokens to survive the move.

How do I move to a new version?

Stop the service, install the new binaries over the old ones, start the service. Schema changes are additive and need no migration step. Take a backup first anyway.

Where are the logs?

In the standard output, which systemd captures: 

sudo journalctl -u sumami -f

Access logs record the method, the path, the status and the duration. Query strings are stripped from logged paths and request bodies are never logged.

Privacy

Does Sumami store IP addresses?

No. Not in the database, not in the logs, and not hashed into a stable identifier. The server uses a coarse IP prefix to derive a rotating, non-reversible id, and then discards the address. The full details are on the privacy page.

Does the tracker set cookies?

No cookies, and no localStorage either. The collection request is sent with credentials: 'omit' so no cookie is attached to it. Nothing about a visit persists in the visitor's browser.

Why is there no country data?

Because Sumami has no geo-IP database and never looks one up. A country is recorded only if a proxy in front of the server sets a header containing it — CF-IPCountry, for example — and you name that header in SUMAMI_COUNTRY_HEADER. Without that, no geography is recorded at all.

What happens if I put an email address in a custom event?

It is stored verbatim, and your installation becomes a system that processes personal data. The privacy guarantees do not apply to it any more, and you take on the obligations that come with that. Use coarse values such as plan: 'free' instead. The privacy page says more.

Is there any telemetry in Sumami itself?

No. The server makes no outbound requests of any kind — no analytics, no crash reporting, no update checks. The dashboard pages make no requests to third parties either: no fonts, no scripts and no images are loaded from anywhere else. You can run the whole thing with the outbound network cut off.

The CLI

Can I read the database without running the server?

Yes, that is what the CLI is for. Copy the .duckdb file to your laptop and run sumami websites --db ./sumami.duckdb. The file is opened read-only.

Why does the CLI need credentials in HTTP mode?

Because in HTTP mode it is a client of the API, and the API is default-deny. It logs in with POST /api/login and caches the token in ~/.config/sumami/credentials.json with mode 0600. Pass --token to skip the cache.

Does the CLI write to my database? Does it modify anything?

Not unless you ask it to. The file is opened read-only, with two exceptions: prune enforces the retention window and erase deletes a website's data. Both ask for confirmation. Neither ever touches a database file that the server currently has open.

Still stuck?

Open an issue at github.com/sumami-dev/sumami/issues. If your problem is a privacy or security issue, please describe it privately to the maintainer instead of opening a public issue with a working exploit or a real leaked value in it.
